---
title: Respect provider feedback
description: Read rate limit headers and pause every worker when the provider asks you to slow down.
---

A provider knows its own counters better than you do. valve reads the rate
limit headers on each response and, when the provider asks for a pause, writes
it to the store so every worker sharing the id waits.

## With fetch

`wrapFetch` observes every response automatically.

```ts
const partnerFetch = partner.wrapFetch(fetch, { retries: 2 });
const res = await partnerFetch('https://api.partner.example/v2/orders');
```

Every response updates provider feedback, even when the request cannot retry.
Automatic retries default to GET, HEAD, OPTIONS, PUT and DELETE. The method
comes from `init.method`, then the `Request` method, then GET.

For an eligible request receiving a 429, or a 503 with a valid `Retry-After`:

1. valve processes provider feedback and establishes a shared pause when a
   positive delay is available. A 429 without a positive provider delay uses
   exponential backoff.
2. It cancels the unused response body to free the connection.
3. It queues the request again at its original position, and releases its
   concurrency slot while waiting.
4. Once the configured retry limit is exhausted, it returns the final response
   unchanged.

The `retries` option specifies additional attempts after the initial request.
The default of `2` permits up to three total requests.

Set `retries: 0` to read feedback without retrying. Network errors and other
HTTP failures are never retried.

A malformed or empty `Retry-After` on a 503 is treated as absent, so the
response is returned without retrying or consuming its body. Zero seconds and
expired HTTP dates are valid and allow a retry without a header-based pause.
A 429 without a positive provider delay still uses exponential backoff.

### Requests with side effects

POST, PATCH and other methods return the first response by default, with its
body available to the caller. Their responses still establish shared pauses.
An `Idempotency-Key` header does not enable retries: providers differ in how
they handle keys, committed operations and error responses.

After verifying the provider's idempotency contract for a specific operation,
create a dedicated wrapper to opt in:

```ts
const createOrderFetch = partner.wrapFetch(fetch, {
  retries: 2,
  retryUnsafeMethods: true,
});
const res = await createOrderFetch('https://api.partner.example/v2/orders', {
  method: 'POST',
  headers: { 'Idempotency-Key': orderOperationId },
  body: JSON.stringify(order),
});
```

The caller must ensure replaying the operation is safe, including reusing the
same key and payload if the provider requires them. PUT and DELETE also need
provider-specific review despite their HTTP idempotent semantics. This option
applies to every request through that wrapper; keep it scoped to operations
you have verified. It does not override `retries: 0` or streamed `init.body`.

**Compatibility change:** earlier versions retried all methods automatically.
POST and PATCH callers now receive the first response unless they explicitly
opt in. Setting only `retries` no longer enables retries for these methods.

### Request bodies

A `Request` object's body is cloned for each attempt. A `ReadableStream`
passed as `init.body` can only be sent once, so that request is never retried.

## With any other client

Use the `observe` run option to map a result to `{ status, headers }`:

```ts
const res = await partner.run(() => got(url, { throwHttpErrors: false }), {
  observe: (r) => ({ status: r.statusCode, headers: r.headers }),
});
```

`observe` only sees results that resolve. If your client throws on 4xx, either
disable that behavior or call `valve.observe()` from your error handler. See
[HTTP clients](/docs/examples/http-clients/) for axios, got, and undici.

You can also call `valve.observe(response)` directly at any time. It returns
`void` and writes the pause in the background.

## Which headers are read

The default reader, `defaultFeedback`, combines three readers and keeps the
longest pause.

| Header                                                              | Read when                  | Pause              |
| ------------------------------------------------------------------- | -------------------------- | ------------------ |
| `Retry-After` (seconds or HTTP date)                                | Status 429 or 503          | The given duration |
| IETF `RateLimit: r=…;t=…`                                           | Any status, `r` is 0       | `t` seconds        |
| `RateLimit-Remaining` and `RateLimit-Reset`                         | Any status, remaining is 0 | The reset duration |
| `x-ratelimit-remaining`, `x-ratelimit-reset` (and `x-rate-limit-*`) | Any status, remaining is 0 | Until the reset    |

A response that reports zero remaining quota pauses the valve even when its
status is 200, so the next request does not have to fail first.

`Retry-After` HTTP dates are compared with the response `Date` header when it
is present. `x-ratelimit-reset` accepts epoch seconds, epoch milliseconds,
relative seconds, or Go-style durations such as `1m30s`.

The IETF reader follows
[draft-ietf-httpapi-ratelimit-headers-11](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-ratelimit-headers-11),
sections 4.1.1 and 4.1.2. The draft can still change.

To change which headers are read, see [Feedback readers](/docs/reference/feedback/).

## When there is no useful header

A 429 without a usable header triggers exponential backoff: 1s, 2s, 4s, and so
on, capped at 30s. Any non-429 response resets the sequence. Configure it
with `backoff: { base, max }`.

`feedback: false` turns header reading off but keeps 429 backoff.

## Cap pauses

`maxPause` (default `'15m'`) caps any single pause that comes from feedback or
backoff, protecting you from a misread or hostile header. A capped pause emits
a `warning` event. Manual `valve.pause()` calls are not capped.

## Pause and resume manually

```ts
await partner.pause('2m'); // Every worker sharing the id waits 2 minutes.
await partner.resume(); // Ends the pause everywhere.
```

Unlike `observe`, `pause` resolves once the store has recorded the pause.
