# Contributing to valve

This repository is a pnpm workspace. The published package is `valvejs` in
`packages/valve`; everything else is private. Changes are judged by
`pnpm check` plus CI suites selected from the changed paths, so the fastest way
to a green PR is to know which rules apply to your change before you start.

Read [references/repo-map.md](references/repo-map.md) for where things live
and how the library is organized internally.

## Setup

Node.js 24 and pnpm 11.28.4 (see `packageManager` and `engines`). Then:

```sh
pnpm install
pnpm build
```

The library supports Node.js 20+ at runtime, but the workspace tooling needs 24.

## Rules CI enforces (easy to trip over)

- **No en or em dashes** in any tracked text file (code, Markdown, MDX, YAML,
  skills). `pnpm check:source` fails on them. Use a period, comma, colon,
  parentheses, or a plain hyphen.
- **Core uses web standard APIs only.** No `node:` imports anywhere in
  `packages/valve/src/`.
- **Zero runtime and peer dependencies** in `packages/valve/package.json`.
- **TODOs** must look like `// TODO(decision|verify|1.0.0): text.` and appear in
  `scripts/todo-register.json`.
- **Prettier formatting** for everything (`pnpm lint` runs `prettier --check .`).
  Run `pnpm format` before committing.
- **Size budgets**: `pnpm check:size` (delegates to `pnpm perf footprint --check`).
  The core, Redis, headers, and group entries each have a gzip ceiling.
- **Coverage thresholds** in `packages/valve/vitest.config.ts`: lines 95,
  branches 90, functions 95, statements 95.
- Each source file opens with a one-line comment stating its purpose; keep
  that convention for new files.

## Which checks to run

| Change                                          | Run before pushing                                                                                   |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Library code in `packages/valve/src`            | `pnpm check` (lint, typecheck, coverage, type tests, build, source, package, size), plus integration |
| Lua scripts in `packages/valve/src/redis/*.lua` | `pnpm --filter valvejs build` (regenerates `scripts.ts`), then `pnpm check` and integration tests    |
| Library tests only                              | `pnpm test`, `pnpm test:types` if types changed                                                      |
| Docs or website (`apps/web`)                    | `pnpm --filter @valve/web test`, `pnpm docs:build`, browser tests when layout changes                |
| Performance-sensitive library code              | Also the perf harness: use the `valve-perf-harness` skill                                            |
| Agent skills (`skills/`, `.claude/skills/`)     | `pnpm lint`, `pnpm check:source`                                                                     |
| Repo scripts or workflows                       | `node --test scripts/*.test.mjs`, `pnpm lint`                                                        |

Integration tests need real stores:

```sh
docker compose -f compose.test.yml up -d   # Redis 6.2, 7.4, 8 and Valkey 7.2, 8
REDIS_URL=redis://127.0.0.1:6379 pnpm test:integration
```

`REDIS_CLUSTER_URL` adds cluster checks; `REDIS_SERVER_BIN` enables the
stop/restart fixture. Never point these at a store with valuable data.

`pnpm examples` runs the six self-checking examples after a build (two need
`REDIS_URL`).

## Library change checklist

1. **Memory and Redis parity.** Admission logic exists twice: TypeScript
   (`algorithms.ts`, `memory-store.ts`, `managed.ts`, `scoped.ts`) and Lua
   (`src/redis/*.lua`). A behavior change needs both, plus tests on both paths.
   `src/redis/scripts.ts` is generated by `scripts/lua-sha.mjs` during build;
   never edit it by hand.
2. **Public API.** Exports live in `src/index.ts` and the subpath entries
   (`redis`, `headers`, `group`). Document new options in the TSDoc on
   `src/types.ts` (TypeDoc renders it), in `apps/web/content/docs/reference/api.mdx`,
   and in the relevant guide. Add type tests in `test/types.test-d.ts`.
3. **Errors.** New failure modes reuse `ValveError` codes; messages name the
   option and suggest a fix.
4. **Guarantees.** If behavior affects bounds, pauses, leases, or store
   failures, update `apps/web/content/docs/guarantees.mdx` precisely. Don't
   overclaim.
5. **Changeset.** Required (see below).
6. **Agent skills.** If the change alters public behavior, defaults, options,
   errors, or recommended patterns, update the user-facing skills in `skills/`
   (see [Keep agent skills in sync](#keep-agent-skills-in-sync)).

## Changesets and versioning

- Run `pnpm changeset` (or add `.changeset/<name>.md`) for any change to
  published library code, package metadata (`packages/valve/package.json`,
  README, LICENSE, NOTICE), or library build configuration, even under a
  `chore:` title. CI requires it.
- Not needed for docs-only, website, tests-only, CI, tooling, perf harness, or
  skills changes. Don't add empty changesets.
- Choose `patch` for fixes, `minor` for compatible features, `major` for
  breaking changes. Write the summary for package users.

```md
---
'valvejs': patch
---

Reject `maxWait` values above the platform timer limit with `INVALID_OPTIONS` instead of firing immediately.
```

- Per `AGENTS.md`: whenever a changeset is added, edited, removed, or consumed,
  update the website changelog in the same work: `pnpm --filter @valve/web sync`
  (never hand-edit the gitignored `content/changelog/` or `.generated/`). See
  [references/releases.md](references/releases.md) for versioning, publishing,
  and post-publish steps.

## Commits, branches, and pull requests

- Conventional Commits for commits and PR titles (`feat:`, `fix:`, `docs:`,
  `chore:`, `refactor:`, `test:`, `perf:`, optional scope like `fix(redis):`,
  `!` for breaking). commitlint runs locally (husky) and on PR titles.
- PRs are squash merged; the PR title becomes the commit subject.
- Branch names: `<type>/<issue-number>-<short-description>` when there is an
  issue, for example `fix/42-scheduler-timing`; `docs/improve-readme` is fine.
- Contributors open PRs from a fork into `ksaurav24/valve:master`.
- Keep prose direct and plain; no long dashes (CI will fail).

## Docs and website

- Docs pages are MDX under `apps/web/content/docs/`; each needs `title` and
  `description` frontmatter and an entry in its directory's `meta.json`. Link
  with `/docs/...` paths and `/api/...` for TypeDoc.
- Content that depends on whether a version is on npm uses `<Published>` and
  `<Unpublished>` wrappers.
- Dev server: `pnpm docs:dev` (http://127.0.0.1:4321). Build: `pnpm docs:build`.
  Browser tests: `pnpm --filter @valve/web test:browser` after installing
  Chromium (`pnpm --filter @valve/web exec playwright install chromium`).
- Never hardcode versions, star counts, downloads, or contributors; they come
  from sync scripts. See `apps/web/README.md`.
- Root `README.md` and `CONTRIBUTING.md` are rendered on the site too.

## Keep agent skills in sync

The user-facing agent skills in `skills/` are published from this repository
(`npx skills add ksaurav24/valve`) and teach agents how to use the public API.
They are only useful if they are correct, so treat them like docs:

- When an option, default, error code, entry point, or recommended pattern
  changes, grep `skills/` for it and update every mention (several skills carry
  their own copy of key facts so each works when installed alone).
- Keep each `SKILL.md` under about 500 lines; move detail into its
  `references/`.
- Skill descriptions decide when agents load them. Edit them deliberately.
- Run `pnpm check:skills` to validate names, metadata, catalogue entries, and
  bundled reference links. Review behavior against the implementation after
  substantive API changes; behavioral evaluations are optional when requested.
- Maintainer skills live in `.claude/skills/` and are marked
  `metadata.internal: true` so the public installer hides them.

## Before you hand off

- `pnpm format`, then the checks from the table above.
- `git status` shows no generated files (`scripts.ts` is committed only when Lua
  changed; `.perf/`, `.generated/`, `content/changelog/` are ignored).
- Changeset present when required, website changelog synced if it was.
- PR description says what changed for users and how it was verified.
